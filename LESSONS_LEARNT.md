# Lessons Learnt

- 2026-09-24: **`new Dictionary()` is SYMBOL-keyed in this project's typing mode — writing a String key into it throws "UnexpectedTypeException: Expected Symbol, given String".** Both `buildFlightReport()` and `saveState()` did exactly that, and both call sites are wrapped in try/catch, so the failure was completely silent: the phone flight report was **never** sent (and view state was never persisted on suspend). A dictionary *literal* (`{ "k" => v }`) creates a String-keyed dictionary and then accepts further String keys — verified in the simulator: `new Dictionary()` + `d["x"]=1` → FAIL, `{ "x" => 1 }` + `d["y"]=2` → OK, `{ "seed" => 0 }` + overwrite → OK. `new Dictionary()` + a symbol key ALSO failed. Rule for this codebase: never `new Dictionary()` when the keys are Strings; seed from a literal. Verified afterwards by dumping the real payload key by key.
- 2026-09-24: Monkey C does not tolerate huge functions: an instrumented test function with ~25 locals, a 22-element literal and a loop crashed at runtime with "Unexpected Type Error / Failed invoking <symbol>" at a `new Dictionary()` line (the app aborted). Splitting the same code into several small functions worked. Practical rule: keep helper functions small, especially in test harnesses.
- 2026-09-24: **A silent try/catch around a whole feature hides its absence.** The phone report had never worked, and nothing in the log said so because the only call site was `try { commsStop.sendFlightStop(..., buildFlightReport(true)); } catch (ex) {}`. When a feature produces no visible effect, instrument the *value* it produces rather than assuming the code path ran.
- 2026-09-24: **You can measure text on the simulated device, so UI fit does not have to be guessed.** `Dc.getTextDimensions(text, font)` accepts a `Graphics.VectorFont` (`Graphics.FontType = FontResource or FontDefinition or FontReference or VectorFont`). A scratch build that printed, per page, the chosen font index, the rendered width and the circle's chord width at that line (`2·sqrt(R²−dy²)`) turned "does it get clipped?" into a table of numbers — e.g. `CHRONO '1:23:45' font#1 w=244 max=248`, `ZULU '16:22' font#0 w=213 max=234`. Because the numbers arrive from the real renderer, this is also how the *effective* font size per page is now chosen: keep a few candidate sizes, measure the string, take the biggest that fits — instead of assuming a per-glyph em width.
- 2026-09-24: Condensed faces buy legibility on a round screen: `RobotoCondensed` sets the same text in ~10% less width than `Roboto`, so at a fixed chord width the glyphs can be *taller* (measured: "16:22" is 213 px at the 0.32·minWh size, i.e. the biggest candidate is used on almost every page). Preferring condensed also means the value column stops being the limiting factor for 5–6 character values.
- 2026-09-24: **"I installed the update and nothing changed" was a STORED SETTINGS problem, not a code problem.** The first "big fields"/paged-face build changed the *default* in `resources/properties/properties.xml` from 0 to 1 — but a value already persisted on the device (the settings blob is seeded from the settings JSON at install time, so `DisplayMode` was already stored as 0) always beats a new default. The app faithfully kept drawing the bezel ring, so the only visible change was the removed QNH. Consequences: (a) never rely on a changed property default to reach existing installs; (b) the effective value must be verified, not assumed — printing `displayMode` in a simulator run showed `0 (RING)`, i.e. the new face had never actually been drawn (my earlier "verification" only proved the page helper functions returned strings, not that `drawPagesView()` ran — a real trap when the draw branch is guarded by the setting). Fix: keep a separate "choice made" key and treat its ABSENCE as the new behaviour, so a lost/slow asynchronous `Properties.setValue()` re-selects the new default instead of pinning the old one.
- 2026-09-24: `Application.Properties.setValue()` is ASYNCHRONOUS and `onShow()` re-reads all settings (`loadSettings()`), so a value written by the on-device settings menu can be read straight back as the previous value and silently revert. Two defences: apply the change to the view directly, and cache the session's choice in a static instead of trusting the property round-trip. Also read the *live* view value when toggling, not the stored property (otherwise a mismatch between an overridden view and a stale property makes the second toggle a no-op).
- 2026-09-24: A round 260 px face can only show one big number legibly, so legibility is a *navigation* problem, not a type-size problem. Final answer for this app: the **paged face** — page 0 is the chrono (the value the pilot looks at 90% of the time, drawn centred with the largest fitting font), then UP/DOWN walk one value per page through everything the ring and the quick-info screens used to show. Layout (fractions of minWh, 260 px): small timer −0.245, separator −0.135, label −0.075, value +0.16, sub-line +0.41, page indicator +0.472; label 0.08, sub 0.065, value candidates 0.32/0.28/0.24/0.20 picked by measured width. Two layout traps found while building it: (a) on the chrono page the timer moves *into* the value slot, so the separator line (at −0.04·minWh) must be skipped or it strikes through the digits; (b) an 8-character "10:23:45" at the 0.26 value size is ~242 px wide against a chord of only 228 px at dy = 0.235·minWh, so the chrono falls back to the 0.21 size for anything longer than 5 characters. Roboto digit advance ≈ 0.56em, colon ≈ 0.27em — use that to budget a string against 2·sqrt(R²−dy²).
- 2026-09-24: Repurposing a key means relocating whatever it did: making UP/DOWN page navigation put the sub-timer on **UP hold** and the map (previously the end of the quick-info chain) on the **MENU**, or functionality is silently lost. Long-press detection must be armed on press and decided on release, and returning `true` from `onKeyPressed` is what stops `BehaviorDelegate` also firing `onNextPage`/`onPreviousPage` — but keep a `onPreviousPage()` fallback that calls the same short-press action, because a touch swipe can trigger it without any key event.
- 2026-09-24: Readability on a 260 px round face — the bezel ring is at its limit: 45° of arc at r≈110 px is ~86 px, so "HDG 330" at the ~21 px label size already fills it and the Bezel Font setting has to stop at 130%. Making type bigger means changing the layout, not the multiplier: (a) drop the label prefixes so the same arc carries a much larger value, (b) one value per page at ~26% of screen height. Geometry rule for centred text on a round screen at vertical offset dy with radius R: the usable half-width is sqrt(R²−dy²) — at dy = 0.27·minWh (70 px of 130 R) that is 110 px, which is what caps a value at about five or six digits wide.
- 2026-09-24: Screenshotting the UI to verify it is NOT practical in this environment: the `view_image` tool does not surface image content here, and a pixel-analysis fallback needs the simulator window bounds, which is not available (`Quartz`/pyobjc is not installed, `screencapture -w` needs a click, and the desktop is dark enough that "find the largest dark blob" cannot isolate the device face — a two-screenshot diff only found the terminal window). Layout changes therefore have to be reasoned geometrically and confirmed by the user on the watch.

- 2026-09-24: **Garmin Connect does NOT display Connect IQ developer data for a SIDELOADED app.** A real 66 min flight recorded with the release build was exported from Garmin Connect and parsed: all 12 dev fields were present and populated (obt/ibt, block_time_s=3983, landings=1, distance_nm=79.9, max_alt_ft=4969, avg_gs_kt=72, max_g=3.33, plus per-second g_force 0.85–2.05 G, bank_deg, pitch_deg over 3984 records), yet nothing appears on the activity page. Garmin Connect matches the FIT developer_data_id application_id against its Connect IQ app catalogue to get the labels/chart metadata (that is what the `fitContributions` block is uploaded for, and what Monkey Graph previews) — a sideloaded app is not in that catalogue, so the fields are stored but never rendered. The data is NOT lost: it survives in the FIT (Garmin's own export keeps it). To display it: publish the app to the Connect IQ store, or surface the numbers in the companion app (the flight report already goes over BLE).
- 2026-09-24: The coordinated-turn bank estimate needs sanity limits: a GPS track jump produced a -71.5° bank in a real log. Clamp the turn rate fed into the model (MAX_TURN_RATE_DEG_S = 15°/s — a standard-rate turn is 3°/s, a steep 60° turn ≈10°/s), require real flying speed (> 40 kt) and a usable fix, and clamp the output to ±60°.

- 2026-09-24: Distance is integrated as `GS × dt` once per second, so every second without a usable speed (GPS lost, stale fix, onUpdate not running under a sub-view) silently loses the metres flown. Fixed by caching the latest accepted fix plus the fix at the last accumulated sample (`fixLatDeg/LonDeg`, `accumRefLat/Lon`, `lastAccumAtMs`) and, whenever accumulation resumes after a gap > `GAP_BRIDGE_MIN_MS` (3 s), adding the great-circle distance between the two. Guards: skip gaps <= 3 s (normal 1 Hz cadence is already covered, bridging then would double count), reject gaps implying > `MAX_BRIDGE_SPEED_MPS` (200 m/s ≈ 390 kt, i.e. a GPS glitch not movement), only bridge with a fix of quality >= 3, wrap-safe timers, and clear the references on reset() so it can never bridge across flights. Note the gap is a straight line, so a curved detour during a long outage is slightly under-counted.

- 2026-09-24: `now - lastLandingAt < MIN_LANDING_GAP_MS` in the touch-down debounce used a RAW subtraction against a sentinel of 0 — and `System.getTimer()` is a signed 32-bit counter, so once the watch passes ~24.8 days of uptime `now` is negative, `now - 0` is negative, the guard returns early and **every landing for the rest of the session is silently dropped** (reported as "a whole flight, 0 landings"). Any timer comparison against a 0/never-set sentinel must go through `elapsedSince()`. Same hazard existed in the taxi-start hold and the GPS-freshness / "fix lost" checks.
- 2026-09-24: Touch-down detection must not depend on AGL alone. AGL = (QNH-corrected baro altitude) − fieldElevation captured at start, so a QNH change during the flight offsets the whole trace and `agl < 50` can become unreachable → all landings lost. Add a speed clause (`airborne` and GS < 15 kt — taxi speed, no aircraft is airborne there) and a safety net in `autoStop()` that counts the landing if the stop happens while still flagged airborne at low speed. Distinguish "speed unknown" (-1) from 0 kt, or a GPS dropout at altitude logs a landing.
- 2026-09-24: Landing logic can be tested in the SIMULATOR (which has no GPS) by patching a scratch copy to call `_updateAirborneState(aglFt, gsKt, now)` directly with scripted values — verifies airborne arming, the debounce, the taxi-speed clause and the autoStop safety net in ~45 s.

- 2026-09-23: Auto-start/auto-stop semantics: the timer must start at OFF-BLOCK (taxi), not at take-off, so OBT is the moment the aircraft begins rolling — a 5 kt threshold held for 5 s (`TAXI_START_SPEED_MS`/`TAXI_START_HOLD_MS`) sits above walking pace (1.6–2.7 kt) but below normal taxi speed, so the pilot walking to the aircraft cannot trigger it. Because a taxi can now stop before take-off, the zero-speed `autoStop()` MUST be gated on `hasTakenOff` (take-off speed reached at least once, persisted in the backup) or any apron/holding stop would silently end the flight.

- 2026-09-23: The landing counter was under-reading because (a) `landings`/`airborne` were NOT in the `Application.Properties` backup, so any mid-flight app kill reset the count, and (b) the take-off/touch-down state machine only ran from `onUpdate()`, which stops running whenever a sub-view (quick info, trip, map, settings) covers the main view — landings that happened while another screen was up were never counted. Fixed with a shared `_updateAirborneState()` called from `onPosition()` too, plus a 20 s debounce and backup persistence.
- 2026-09-23: G-force has no native API. Use the wrist accelerometer magnitude — `Sensor.Info.accel` (Array, milli-g) or the batched `AccelerometerData.power` from `registerSensorDataListener({:accelerometer => {:includePower => true}})`. Magnitude is orientation independent, so `sqrt(x²+y²+z²)/1000` ≈ load factor; it is the WRIST IMU though, so wrist movement is included — indicative, not a calibrated g-meter. `AccelerometerData.x/y/z/power` are Arrays of samples per period, so average the batch before use.
- 2026-09-23: The Connect IQ SIMULATOR NEVER PRODUCES ACCELEROMETER DATA (`Sensor.getInfo().accel == null`, the sensor-data listener never fires) — G-force/bank/pitch graphs can only be verified on a real watch. `Sensor.registerSensorDataListener()` itself works in the simulator (no exception), which makes this easy to misdiagnose.
- 2026-09-23: To verify what actually lands in the FIT file: the simulator writes saved activities to `$TMPDIR/com.garmin.connectiq/GARMIN/Activities/*.fit` (i.e. `/var/folders/.../T/...` when TMPDIR is redirected to the SSD). `monkeydo` cannot press watch buttons, so copy the project to a scratch dir, patch `onUpdate()` to auto-drive start → arm → stop, build that, and parse the resulting FIT (see the dev-field/PIT lesson below).
- 2026-09-23: FIT developer fields — `MESG_TYPE_SESSION` fields appear in the Garmin Connect activity summary; `MESG_TYPE_RECORD` fields need `displayInChart="true"` + `chartTitle` + `fillColor` in `resources/fit/fit.xml` to become a per-second GRAPH. Session values are written once at the end of the recording, so `setData()` must run before `Session.stop()`/`save()`; record values must be pushed about once per second or the graph has gaps. The FIT carries only the numbers — the labels/units shown by Garmin Connect come from the app's fitContributions metadata, and the field name/units in each `field_description` message (`createField` name/units).
- 2026-09-22: `Toybox.FitContributor` needs its OWN `<iq:uses-permission id="FitContributor"/>` in `manifest.xml` — the existing `Fit` permission only covers `Toybox.ActivityRecording`. Without it `monkeyc` fails with `Permission 'FitContributor' required for '$.Toybox.FitContributor'`.
- 2026-09-22: FIT developer fields only show up in Garmin Connect if their `resources/fit/fit.xml` `fitField id` matches the field id passed to `Session.createField()`. Also: `dataLabel`/`unitLabel` must be real string resources (the compiler validates them and fails the build on a bad `@Strings.x` reference), `displayInActivitySummary="true"` is what puts them in the activity summary, and `Session.createField()` must be called AFTER `Session.start()` (same order as Garmin's MO2Display sample), guarded with `has :createField`.
- 2026-09-22: `MESG_TYPE_SESSION` developer fields are written once, at the END of the recording — call `setData()` before `Session.stop()`/`save()` or the values (e.g. IBT, landings) are lost. `createField()` on a session also has `:count` for `DATA_TYPE_STRING` = max string bytes + null terminator.
- 2026-09-08: `System.getTimer()` is a signed 32-bit ms counter that wraps after ~24.8 days of uptime, so `now - start` can go negative/wrong. Compute elapsed by interpreting both values as unsigned 32-bit in 64-bit (`now.toDouble()` and add `4294967296.0` when negative) so a single wrap stays correct. Use this for the main timer, sub-timer, and their persistence.
- 2026-09-08: The altitude alert was one-shot per flight; re-arm both flags when the aircraft moves more than the 200 ft lead away from the target (hysteresis) so repeated level-off / cross events alert again.
- 2026-09-08: `WatchUi.View.onHide()` fires whenever a subview is `pushView`-ed over the main view — NOT only when the app exits. Disabling location events there froze GPS mid-flight (timer went red, altitude/V-S stalled). Fix: skip disabling while `running`.
- 2026-09-08: An unconditional `WatchUi.requestUpdate()` at the end of `onUpdate()` runs a continuous redraw loop at full frame rate (huge battery drain). Throttle via a `_lastRefresh` gate (1 Hz) for quick-info/trip screens.
- 2026-09-08: Treating a null altitude reading as 0 ft AGL caused false "landing" counts during momentary sensor dropouts. Gate airborne/landing + circuit logic on altitude availability.
- 2026-09-08: `restartGps()` was a no-op, so changing GPS mode in the settings menu never re-subscribed — call `loadSettings()` (which re-registers `enableLocationEvents`) instead.
- 2026-09-08: Bezel text radius compensation must use the SCALED label size (`bezelLblFaceSize`), not the nominal `minWh * 0.082`, or top fields overlap the ring when the font scale is >100%.
- 2026-09-08: JSON payloads from the phone encode integral numbers as `Number` and decimals as `Double` — a hard `as Float` cast on lat/lon throws and silently drops the whole flight plan. Normalise with an `instanceof`-based `coerceFloat` helper.
- 2026-09-08: A sub-timer killed while running was restored frozen at 0:00 because backup saved the stale `subTimerElapsed`. Save the live elapsed (`now - subTimerStart`) at backup time.
- 2026-09-08: Vertical-speed/FPM bug: the old code picked baro altitude if present else GPS *per sample*, but QNH-baro and GPS (ellipsoid MSL) sit on different datums (often 100s of ft apart), so alternating sources produced bogus V/S spikes. Fix: use ONE source (the AltitudeSource setting) and never mix between consecutive samples (`lastAltSource` guard); require a longer sample spacing (1 s vs 0.5 s) for noisier GPS altitude.
- 2026-09-08: `Dc.drawRadialText` radius semantics differ by direction: `RADIAL_TEXT_DIRECTION_CLOCKWISE` extends glyphs OUTWARD from the given radius, `COUNTER_CLOCKWISE` extends them INWARD. To make top and bottom bezel fields share the same visual ring, use `radius = ring − textHeight` for clockwise fields and `radius = ring` for counter-clockwise fields.
- 2026-09-08: `Dc.drawRadialText` requires a `Graphics.VectorFont` and its direction parameter is typed `Graphics.RadialTextDirection` — passing a plain `Number` fails strict type-check (`Invalid ... passed as parameter 8 of type ... RadialTextDirection`).
- 2026-09-08: Monkey C `Math` has no `Math.abs` — compute `x < 0 ? -x : x` manually.
- 2026-09-08: The hand-rolled per-character bezel renderer (48-slot math + drawAngledText folds) was retired in favour of the native `drawRadialText` API — far simpler and matches how Garmin's own faces draw bezel labels.
- 2026-09-08: SDK 9.1 exposes the on-watch IMU via `Sensor.registerSensorDataListener` (accelerometer with `:includePitch/:includeRoll`, gyroscope deg/s, magnetometer). BUT the sensor measures the WRIST, not the aircraft, so it is unreliable for aircraft bank/attitude. Aircraft bank is better derived from GPS track rate + groundspeed: `bank ≈ atan(turnRate·GS/g)` (coordinated-turn model).
- 2026-09-08: Idle-clock redraws were redrawing every frame and draining battery; gate `WatchUi.requestUpdate()` behind a refresh policy (full speed only while running/flashing; 1 Hz while armed/acquiring; ~5 s when idle).
- 2026-07-14: Vertical speed (V/S) was jittery because it was computed as a raw instantaneous derivative between consecutive altitude samples; fixed by adding an EMA low-pass filter (α=0.15) and a 500ms minimum sample-interval gate so that closely-spaced baro/GPS samples don't amplify noise. Raw V/S is still used for fast tendency detection; smoothed V/S feeds display and BLE telemetry.
- 2026-04-27: `monkeyc -f monkey.jungle` must be used instead of `manifest.xml` to avoid jungle parser StackOverflowError.
- 2026-04-27: Connect IQ does NOT support reflection or dynamic symbol lookup on typed objects. Typed objects such as `Position.Info` must be accessed with dot syntax (for example `pInfo.course`, `pInfo.heading`). Using `pInfo["course"]` or `pInfo[:course]` will return `null`, cause an "Undefined symbol" compile error, or crash at runtime depending on SDK version. The correct portable pattern is to read `pInfo.course` and check for `null` before using.
- 2026-04-27: Monkey C arrays created with `[]` are zero-size; index-assigning (e.g., `slots[0] = x`) crashes with Array Out Of Bounds — use `new [N]` for fixed-size or `.add()` for dynamic growth.
- 2026-05-22: `Sensor.getInfo().pressure` is in Pascals (~101325 at sea level), NOT hPa. Always call `VFRAvionicsData.pressureToHpa()` before applying the pressure-altitude formula `145366.45 * (1.0 - pow(hPa/1013.25, 0.190284))`. Using raw Pa divides by the hPa reference (1013.25), producing a ratio of ~100 and a computed altitude of ~−138 000 ft, which silently forces `transitionActive = false` every onPosition() tick and permanently breaks Flight Level display when the barometric sensor is available.
- 2026-05-22: Ground speed display: use `Math.round(speed * 1.94384).toNumber()` not `.toNumber()` alone — the conversion from m/s to kt often ends just below a whole-number boundary (e.g. 30 kt = 15.43 m/s → 29.99 kt), so truncation shows 29 instead of 30. Always round before converting to String for GS display.
- 2026-05-22: Sub-timer state 1 ("running") must be frozen to state 2 ("paused") when restoring from a backup, because `subTimerStart` holds a `System.getTimer()` snapshot from the previous app session; computing `now − subTimerStart` across a kill/restart produces an enormous or negative elapsed value.
- 2026-05-14: FL/QNH behaviour was only half-implemented: `altStr` correctly switched to "FLxx" when `transitionActive`, but `qnhDisplay` still showed live pressure. Fixed by making `qnhDisplay = transitionActive ? "1013" : VFRAvionicsData.formatQnh(qnhInfo)`.
- 2026-05-14: `VFRHeading.getHeadingDeg()` was always reading the compass first, so GPS track was never shown. At aviation speed (≥15 m/s / ~30 kts) GPS track (direction of movement) should take priority over compass (magnetic heading); compass is only preferred when slow/stationary.
- 2026-05-22: Four edge-cases fixed in `VFRHeading.getHeadingDeg()`: (1) Old step 1 (>= 15 m/s) was dead code — step 2 (> 1.5 m/s) was identical and caught it first; collapsed into a single GPS-track branch. (2) The bearing-from-fixes fallback called `Position.getInfo()` a second time — refactored to reuse the position read at the top of the function. (3) Fallback bearing was computed even when device was stationary (two identical fixes → `atan2(0,0) = 0` → spurious north reading "000" instead of "--"); added a minimum movement guard (~5 m squared). (4) `lastLat/lastLon` was updated even when no bearing was computed (first-fix path), meaning the next call always had a stale "last" position; fixed by only updating last-position in the correct branches.
- 2026-04-27: `new Array()` in Monkey C returns an Object, not an Array, so `.add()` fails with UnexpectedTypeException; always use `[]` + `.add()` or `new [N]` literals.
- 2026-04-27: `dc.getTextWidth()` / `Graphics.getTextWidth()` are not available in SDK 9.1; use per-character pixel estimation instead.
